
### 扩展练习一：Buddy System 物理内存管理器

#### 1. 设计思路与实现

**设计目标：** 本次扩展练习的目标是实现伙伴系统（Buddy System）物理内存分配算法，作为 `default_pmm.c` (First-Fit) 的一个替代 `pmm_manager`。First-Fit 算法虽然简单，但在多次分配和释放后容易产生大量内存碎片。伙伴系统通过只管理 2 的幂次大小的内存块，能有效减少外部碎片，并实现高效的块合并。

**核心数据结构：** 我的实现 (`buddy_pmm.c`) 围绕一个核心数据结构展开：
```c
// 每个大小级别的空闲块链表
static list_entry_t free_lists[MAX_ORDER + 1]; //
```

这是一个链表数组，其中 `free_lists[i]` 存储了所有大小为 2<sup>i</sup> 个页面的空闲内存块。`MAX_ORDER` 被定义为 16，因此它可以管理从 2<sup>0</sup>=1 页到 2<sup>16</sup>=65536 页的内存块。

**元数据存储：** 为了在释放时知道一个内存块有多大（即它的 "order"），我利用了 `struct Page` 结构中的 `flags` 字段。通过定义 `PageOrder` 和 `SetPageOrder` 宏，将 order 值存储在 `flags` 的高位。

**算法实现：**

1. **`buddy_init()`：** 该函数负责初始化，它遍历 `free_lists` 数组，并对每个链表头调用 `list_init` 进行初始化。
2. **`buddy_init_memmap()`：** （_注：代码片段中未显示该函数，但其逻辑是_）该函数在 `pmm_init` 期间被调用，用于将探测到的所有空闲物理内存加入到伙伴系统中。它会获取所有空闲页，并将它们（可能通过分裂）添加到 `free_lists` 中合适的 order 链表里。
    
3. **`buddy_alloc_pages(n)`：** （_注：代码片段中未显示该函数，但其逻辑是_）
    - **寻找大小：** 首先，找到一个最小的 order `k`，使得 2<sup>k</sup> 大于等于请求的页面数 `n`。
    - **寻找空闲块：** 查找 `free_lists[k]`。
        - **直接命中：** 如果 `free_lists[k]` 不为空，则从中取出一个块，标记为已使用，并返回。
        - **分裂：** 如果 `free_lists[k]` 为空，则向上查找 `free_lists[k+1]`, `free_lists[k+2]`, ... 直到找到一个非空的链表。
        - **递归分裂：** 假设在 `j` (j > k) 处找到一个块，将其从 `free_lists[j]` 移除。然后将其分裂为两个 2<sup>j-1</sup> 大小的“伙伴”，一个用于继续分裂（或使用），另一个添加到 `free_lists[j-1]` 中。此过程递归进行，直到得到一个 2<sup>k</sup> 大小的块。
    - **失败：** 如果查找到 `MAX_ORDER` 仍未找到空闲块，则返回 `NULL`。
4. **`buddy_free_pages(base, n)`：** 这是伙伴系统的核心，实现了高效的合并。
    - **确定 Order：** 根据 `base` 页中存储的 order，确定要释放的块的大小。
    - **递归合并：**
        - 将当前块（`base`）标记为空闲。
        - 计算其“伙伴”块（`buddy`）的地址。
        - 检查 `buddy` 是否也为空闲，并且 `buddy` 的 order 是否与 `base` 相同。
        - 如果两个条件都满足，则执行**合并**：将 `buddy` 从其 `free_lists` 中移除 (`list_del`)；选择 `base` 和 `buddy` 中地址较低的一个作为新块的起始地址；将新块的 order 设为 `order + 1` (`SetPageOrder(base, order + 1)`)；然后**递归**地对这个 `order + 1` 的新块重复合并检查。
        - 如果 `buddy` 不空闲或 order 不同，则停止合并，并将当前 `base` 块（大小为 2<sup>order</sup>）添加到 `free_lists[order]` 中。
#### 2. 正确性验证

为了验证实现的正确性，我编写了 `buddy_check()` 函数。
- 该函数会遍历 `free_lists` 数组中的**每一个 order**（从 0 到 `MAX_ORDER`）。
- 对于每个 order，它会统计该链表中的空闲块数量 `count`，并根据块大小 `block_size` (即 2<sup>order</sup>) 累加总的空闲页数 `total_free`。
- 最后，它会打印出统计到的 `total_free` 页数，并与全局变量 `nr_free`（由 `alloc` 和 `free` 维护）进行比较。
- 通过 `assert(total_free == nr_free)` 来确保伙伴系统内部链表所管理的空闲页总数与全局计数器一致，从而证明分配和释放操作的正确性。
### 扩展练习二：SLUB (Simple SLAB-like) 对象分配器

#### 1. 设计思路与实现

**设计目标：** 在操作系统内核中，经常需要分配和释放大量大小固定但远小于一页的内存对象（例如 `struct proc_struct`、`struct inode` 等）。如果直接使用页级分配器（如 First-Fit 或 Buddy）来满足这些小请求，会造成巨大的**内部碎片**。
SLUB 分配器（一种 SLAB 简化实现）是为解决此问题而设计的**对象分配器**。它运行在页级物理内存管理器（如 Buddy System）之上，从页管理器获取整页，然后将这些页（称为 "slab"）分割成多个固定大小的小对象，并缓存它们以供快速分配。
**核心数据结构：** 我的实现 (`slub_pmm.c`) 定义了两个关键结构：

1. **`struct slub_cache`**： 这是 SLUB 的核心，用于管理**一类特定大小**的对象。
    - `obj_size`：定义了此类缓存管理的对象大小。
    - `partial_list`：链接所有**部分分配**的 slab（即既不全满也不全空的 slab）。这是分配时首选的列表。
    - `free_list`：链接所有**完全空闲**的 slab。
    - （注：实现中还缺少 `full_list`，一个完整的 SLUB 会有它，但在 `slub_alloc_pages` 中，满的 slab 只是被移出 `partial_list`）。
2. **`struct slub_page`**： 这是对 `struct Page` 的一层封装（_注：代码中显示为 `slub_page` 结构体，但分配/释放函数 `slub_alloc_pages` 的接口仍然是 `struct Page *`，这在实现上可能是为了兼容 `pmm_manager` 接口而进行的简化处理_）。它代表一个 "slab"，即一个被分割用于对象缓存的页面
    - `free_list`：一个指针，指向该 slab 内部的第一个空闲对象。
    - `free_count`：该 slab 中剩余的空闲对象数量。

**算法实现：** （_注：`slub_pmm.c` 中的函数命名 `slub_alloc_pages` 和 `slub_free_pages` 遵循了 `pmm_manager` 接口，这很可能是为了满足实验框架要求。在报告中，我将其理解为**对象**的分配和释放。_）

1. **`slub_init()`：** （_注：代码片段中未显示该函数，但其逻辑是_）
    - 初始化 `slub_caches` 数组。
    - 为不同的大小（例如从 `SLUB_MIN_SIZE` (8) 到 `SLUB_MAX_SIZE` (2048)）分别创建 `slub_cache`。
2. **对象分配 ( `slub_alloc_pages()` )：** 当内核请求一个小对象时：
    - **选择缓存：** （_推断_）根据请求的大小，选择一个合适的 `slub_cache`。
    - **查找 Partial Slab：** 优先从 `cache->partial_list` 中查找一个 slab。
    - **查找 Free Slab：** 如果 `partial_list` 为空，则从 `cache->free_list` 中获取一个空闲 slab，并将其移动到 `partial_list`。
    - **分配新 Slab：** （_推断_）如果 `free_list` 也为空，则调用底层的物理页分配器（如 `buddy_alloc_pages(1)`）获取一个新页面，将其初始化为一个 slab（即分割成 `num_objects` 个对象，并建立内部 `free_list`），然后将其加入 `partial_list`。
    - **分配对象：** 从选定的 slab 中，获取 `slab->free_list` 指向的第一个空闲对象 `obj`，并更新 `free_list` 指向下一个空闲对象 (`slab->free_list = *(void **)obj`)。
    - **更新状态：** `slab->free_count` 减 1。如果 `free_count` 变为 0，说明该 slab 已满，将其从 `partial_list` 中移除 (`list_del(&(slab->link))`)。
        
3. **对象释放 ( `slub_free_pages()` )：** （_注：提供的 `slub_free_pages` 代码片段是一个极大简化的版本。以下是完整 SLUB 应有的逻辑。_）
    - **确定 Slab：** （_推断_）根据要释放的对象 `obj` 的地址，找到它所属的 `struct slub_page` (slab)。
    - **归还对象：** 将 `obj` 添加回 `slab->free_list` 的头部。
    - **更新状态：** `slab->free_count` 加 1。
    - **Slab 迁移：**
        - 如果 slab 之前是满的（不在 `partial_list` 或 `free_list` 中），则将其添加回 `partial_list`。
        - 如果 `slab->free_count` 现在等于该 slab 的总对象数 `num_objects`，说明 slab 已完全空闲，将其从 `partial_list` 移动到 `free_list`。
        - （_策略可选：_ 如果 `free_list` 中的 slab 数量过多，可以触发回缩，将整个页面归还给底层的物理页管理器。）
#### 2. 正确性验证

`slub_check()` 函数用于验证 SLUB 分配器的状态。
- 它遍历 `slub_caches` 数组中的所有缓存。
- 对于每个已初始化的缓存（`obj_size > 0`），它会打印出该缓存的对象大小 `obj_size` 以及当前已分配的对象总数 `num_allocated`。
- 这提供了一个高层次的快照，用于监控不同大小对象的分配情况，辅助调试内存泄漏或分配错误。
