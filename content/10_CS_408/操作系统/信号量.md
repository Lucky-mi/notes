# 信号量机制 (Semaphore)

## 1. 为什么要发明它？

之前讲的 TSL/Swap 都有一个致命弱点：**忙等 (Busy Waiting)**。

- 进程进不去临界区，就在 CPU 上 `while` 死循环。
    
- Dijkstra (迪杰斯特拉) 觉得这样太蠢了。他想：**“如果资源不够，进程应该主动让出 CPU 去睡觉；等资源够了，再由别人把它叫醒。”**
    

于是，信号量诞生了。

---

## 2. 信号量的定义

信号量 $S$ 不再只是一个简单的整数，而在逻辑上被扩展了。

在 408 中，你主要会遇到两种类型：

### (1) 整型信号量 (Integer Semaphore)

- **定义**：就是一个整数，代表资源的数量。
    
- **逻辑**：
    
    - `Wait(S)`: 只要 $S \le 0$，就 `while` 循环等待；否则 $S = S - 1$。
        
    - `Signal(S)`: $S = S + 1$。
        
- **考研评价**：
    
    - **这是个反面教材！**
        
    - 因为它虽然叫信号量，但检查逻辑里还是 `while` 循环。
        
    - **结论**：它**未**解决“忙等”问题。
        

### (2) 记录型信号量 (Record Semaphore) #核心考点

这才是我们做题时默认使用的信号量。它是一个 `Struct` (结构体)。

```c
typedef struct {
    int value;         // 资源剩余数量
    struct process *L; // 等待队列 (链表)，睡着的进程都在这排队
} semaphore;
```

- **value**：代表资源数量。
    
- **L (List)**：是一个队列。当资源不够时，进程不是原地空转，而是把自己挂到这个队列里去**睡觉**。
    

---

## 3. P 操作与 V 操作 (原语详解)

Dijkstra 是荷兰人，所以用了荷兰语单词的首字母：

- **P 操作** (Proberen, 测试)：申请资源 $\approx$ `wait` / `down`。
    
- **V 操作** (Verhogen, 增加)：释放资源 $\approx$ `signal` / `up`。
    

> [!IMPORTANT] 408 必背逻辑
> 
> 必须能够默写出 P/V 操作的内部逻辑，这是分析死锁和复杂同步问题的基础。

### [[P操作]] (申请资源)

**逻辑推演：**
  
1. **先减资源**：不管够不够，先预订一个 (`S.value--`)。
    
2. **判断状态**：
    
    - 如果减完后 $S.value < 0$：说明刚才已经是 0 了，你减成了负数。意味着**资源不够**。
        
    - **动作**：调用 `block()` 原语，把自己变成**阻塞态**，扔进等待队列 $L$。
    
```c
void P(semaphore S) {
    S.value--;
    if (S.value < 0) {
        block(S.L); // 自己去睡觉，让出 CPU！(实现了让权等待)
    }
}
```
  
### [[V操作]] (释放资源)

**逻辑推演：**

1. **先还资源**：用完了，还回去 (`S.value++`)。
    
2. **判断状态**：
    
    - 如果加完后 $S.value \le 0$：这说明什么？说明在你还资源之前，数值是负的（比如 -2），这意味着**队列里还有人在排队**。
        
    - **动作**：调用 `wakeup()` 原语，从队列 $L$ 里拎出一个倒霉蛋，把它唤醒（变成就绪态）。
        
```c
void V(semaphore S) {
    S.value++;
    if (S.value <= 0) {
        wakeup(S.L); // 叫醒等待队列里的一个进程
    }
}
```

> [!NOTE] 难点辨析：为什么 V 操作是 <= 0？
> 
> 假设 $S.value = -2$ (表示有 2 个进程在睡)。
> 
> 我执行 V 操作，$S.value$ 变成 $-1$。
> 
> 虽然我还了一个，但数值依然是负的，说明还是有人在等。所以必须唤醒一个。
> 
> 只有当 $S.value$ 变成 $1$ 时，才说明没人排队。

## 4. 信号量数值的物理含义 (做题金钥匙)

在做选择题时，盯着 $S.value$ 的值，就能读懂系统的状态：

|**S.value 的值**|**物理含义**|
|---|---|
|$S > 0$|当前还有 **$S$ 个可用资源**。|
|$S = 0$|资源刚好用完，且**没有**进程在等待。|
|$S < 0$|资源用完了，且有 **$|

例子：

$S.value = -3$。这意味着：目前资源数为 0，且有 3 个进程正在阻塞队列里排队。

## 5. 信号量的两大应用模型

信号量极其强大，它既能管“互斥”，也能管“同步”。

### (1) 实现互斥 (Mutex)

这是为了保护临界区（如：打印机、全局变量）。

- **初始值**：`mutex = 1` (只有一把钥匙)。
    
- **模板**：

    ```c
    semaphore mutex = 1;
    
    P(mutex); // 拿钥匙，关门
    // --- 临界区 ---
    // 比如：count++
    // --------------
    V(mutex); // 还钥匙，开门
    ```
    
- **特点**：P 和 V 在**同一个进程**中成对出现。夹在中间的就是临界区。
    

### (2) 实现同步 (Synchronization)

这是为了控制执行顺序（如：先生产，后消费）。

- **初始值**：`S = 0` (一开始啥也没有，消费者必须等)。
    
- **模板**：
    ```c  
    semaphore S = 0;
    
    // 进程 A (先干活的)
    {
        // 干活...
        V(S); // 活干完了，通知 B 既然可以开始了
    }
    
    // 进程 B (后干活的)
    {
        P(S); // 检查 A 干完没？没干完我就睡，干完了我就往下走
        // 继续干活...
    }
    ```
    
- **特点**：P 和 V 在**不同进程**中出现。**前操作执行 V，后操作执行 P**。
    

---

## 6. 总结 (Obsidian Note)

- **核心升级**：从 TSL 的“忙等”升级为记录型信号量的“阻塞/唤醒”。
    
- **满足准则**：完美满足了 [[让权等待]]。
    
- **P 操作 (Wait)**：`value--`。如果 `< 0`，去睡觉。
    
- **V 操作 (Signal)**：`value++`。如果 `<= 0`，唤醒别人。
    
- **应用口诀**：
    
    - **互斥**：初值为 1，P/V 夹紧临界区。
        
    - **同步**：初值为 0，前 V 后 P。
