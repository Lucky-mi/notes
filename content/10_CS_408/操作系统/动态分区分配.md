# 深度专题：动态分区分配算法竞技场

> [!ABSTRACT] 核心场景
> 
> 内存中有一堆杂乱的空闲洞（Holes）。
> 
> - **输入**：一个进程请求 $N$ 字节的内存。
>     
> - **输出**：决定把哪一个空闲洞切一块给它。
>     
> - **目标**：速度快，且尽量减少之后无法利用的“碎片”。
>     

我们通过一个具体的内存快照来对比四大金刚：

假设空闲分区链表按地址顺序排列如下：

[8MB] -> [12MB] -> [22MB] -> [10MB] -> [30MB]

当前请求： 申请 11MB。

---

## 1. 首次适应算法 (First Fit) —— 唯快不破

这是最简单、也是最常用的算法。

- **算法细节**：
    
    - **数据结构**：空闲分区链表按**物理地址递增**次序排列。
        
    - **逻辑**：从头开始查找，找到**第一个**能装下的空闲区，然后切分。
        
- **演示**：
    
    - 查 `[8MB]` -> 不够。
        
    - 查 `[12MB]` -> **够了！**
        
    - **动作**：切出 11MB 给进程，剩下一个 `1MB` 的小洞（碎片）。
        
- **考点/评价**：
    
    - **优点**：**最快**（平均查找次数少），且在高地址部分保留了大的空闲区（因为总是先用低地址的）。
        
    - **缺点**：低地址部分会留下很多极小的碎片，每次查找都要跨过它们，增加了开销。
        

## 2. 邻近适应算法 (Next Fit / Cyclic First Fit) —— 均匀撒盐

它是 First Fit 的变体，为了解决 FF “每次都从头查，累死人”的问题。

- **算法细节**：
    
    - **数据结构**：**循环链表**（地址递增）。
        
    - **逻辑**：不再从头查，而是从**上一次分配结束的位置**开始往下查。
        
- **演示**：
    
    - 假设上次分配是在 `[22MB]` 那里结束的。
        
    - 这次直接从 `[10MB]` 开始查 -> 不够。
        
    - 查 `[30MB]` -> **够了！**
        
    - **动作**：切分 30MB。
        
- **考点/评价**：
    
    - **优点**：查找开销非常均匀，不会堆积在头部。
        
    - **缺点 (致命)**：**它破坏了大的空闲区**。因为它是“轮着来”的，会导致内存末尾的大洞也被切得碎碎的。当大进程来时，往往无处容身。
        

## 3. 最佳适应算法 (Best Fit) —— 完美主义的陷阱

- **算法细节**：
    
    - **数据结构**：空闲分区链表按**容量递增**次序排列（从小到大）。
        
    - **逻辑**：找到能满足要求的、且**大小最小**的空闲分区。（为了不浪费大洞）。
        
- **演示**：
    
    - 逻辑上它会遍历所有洞，比较大小差值：
        
        - `12 - 11 = 1MB` (剩余) -> **选中！**
            
        - `22 - 11 = 11MB`
            
        - `30 - 11 = 19MB`
            
    - **动作**：选中 `[12MB]` 那个洞进行切分。
        
- **考点/评价**：
    
    - **优点**：确实保留了最大的空闲区（大洞没被切）。
        
    - **缺点 (常考)**：**产生了最多的外部碎片！**
        
    - **为什么？** 因为它总是去切那个“刚刚好”的洞，切完剩下的那部分（比如 1MB）通常小到谁都用不了，被称为 **“锯末” (External Fragmentation)**。
        

## 4. 最坏适应算法 (Worst Fit) —— 豪迈的切分

- **算法细节**：
    
    - **数据结构**：空闲分区链表按**容量递减**次序排列（从大到小）。
        
    - **逻辑**：总是挑选**最大**的空闲区进行切分。
        
- **演示**：
    
    - 直接找最大的 `[30MB]`。
        
    - **动作**：切出 11MB，剩下 `19MB`。
        
- **考点/评价**：
    
    - **优点**：切完剩下的洞通常还很大（19MB），很有可能还能给下一个进程用。**产生的碎片最少**。
        
    - **缺点**：**杀鸡取卵**。大空闲区被迅速消耗，真正的大进程来了就傻眼了。

## 📊 核心对比表 (408/面试 必背)

|**维度**|**First Fit (FF)**|**Next Fit (NF)**|**Best Fit (BF)**|**Worst Fit (WF)**|
|---|---|---|---|---|
|**排序方式**|地址递增|地址递增 (循环)|**容量递增**|**容量递减**|
|**算法复杂度**|$O(N)$ (但常数小)|$O(N)$ (从上次断点)|$O(N)$ (需排序或全扫描)|$O(N)$ (需排序或全扫描)|
|**碎片特点**|低地址端积累小碎片|全局细碎，无大洞|**极多不可用的微小碎片**|无小碎片，但无大洞|
|**大进程分配**|**好** (保留了高地址大洞)|**最差** (大洞都被切碎了)|**好** (尽量不动大洞)|**差** (专挑大洞切)|
|**综合性能**|**⭐⭐⭐⭐⭐ (通常最优)**|⭐⭐⭐|⭐⭐|⭐⭐⭐|

> [!FAILURE] 常见陷阱
> 
> 问：哪种算法查找速度最快？
> 
> - 如果你回答 Worst Fit，理由是“只要看第一个（最大的）就行了”，这是**半对半错**。
>     
> - **纠正**：查找确实是 $O(1)$（如果维护了有序链表/最大堆）。但是**维护这个有序性**（回收内存时重新排序）需要 $O(\log N)$ 或 $O(N)$。
>     
> - **First Fit** 不需要重新排序，直接插回地址位置即可，综合开销往往最小。
>

## 🧩 内存回收的“四个邻居” (合并细节)

除了分配，**回收 (Deallocation)** 也是考点。当一个进程释放内存时，我们需要检查它的前后是否有空闲区，如果有，必须**合并 (Coalescing)**。

假设释放的分区是 $X$：

1. **前空后不空**：$X$ 与前一个空闲区合并，修改前一个的大小。
    
2. **前不空后空**：$X$ 与后一个空闲区合并，修改链表指向。
    
3. **前后都空**：**三合一！** (前 + $X$ + 后) 变成一个超级大洞，并在链表中删掉后面那个节点。
    
4. **前后都不空**：在链表中插入一个新节点 $X$。
    

> [!CODE] 伪代码逻辑 (前空后不空的情况)
> 
> ```c
> if (free_list[i].end == X.start) {
>     // 向前合并
>     free_list[i].length += X.length;
>     // 不需要创建新节点，直接延长前一个洞即可
> }
> ```

## 🔗 关联思考

现在，你对这些“古老”的算法有了深刻理解。

- **思考**：为什么现代操作系统（Windows/Linux）的主流内存管理不用这些？
    
- **答案**：因为**碎片问题 (Fragmentation)** 实在太难彻底解决，而且**内存紧缩 (Compaction)** 太慢。
    
- 这就是为什么我们一定要引入 **Phase 2 的分页 (Paging)** —— 既然“找大小合适的连续洞”这么麻烦，不如干脆把所有洞都切成一样大的 4KB，那就永远不需要“挑选”了！# 深度专题：动态分区分配算法竞技场
