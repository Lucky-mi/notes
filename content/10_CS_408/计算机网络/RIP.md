### 1. 核心人设：RIP 是个什么样的“人”？

如果在路由协议大家族里搞人设：

- **RIP** 是一个**爱传闲话的老好人**。
    
- **特点：** 也就是**距离向量 (Distance-Vector)** 算法的核心思想。
    
    1. **仅和邻居说话：** 它只和直接相连的路由器交换信息。
        
    2. **毫无保留：** 它把自己知道的**全部**路由表都告诉邻居。
        
    3. **按时打卡：** 无论网络有没有变动，每隔 **30秒** 就把废话（路由表）再说一遍。
        

> **🎓 考研必记基础：**
> 
> - **应用层协议：** RIP 实际上是运行在应用层的，它使用 **UDP** 协议进行传输（端口 **520**）。
>     
> - **度量值 (Metric)：** 使用 **“跳数” (Hop Count)**。每经过一个路由器，跳数 +1。
>     
> - **极限：** 15 跳为最大可达距离，**16 跳表示不可达（无穷大）**。这限制了 RIP 只能用于小型网络。
>

### 2. 核心算法：距离向量算法 (Bellman-Ford)

这是考研**大题计算**的绝对重点。当路由器 A 收到邻居 B 发来的路由表时，A 是如何更新自己的小本本的？

#### 📜 算法逻辑（三步走）

假设路由器 **A** 收到了来自邻居 **B** 的路由表：

1. **“加工”：** A 先把 B 发来的表中，所有条目的“下一跳”改成 **B**，所有的“距离”都 **+1**。
    
    - _潜台词：_ “既然是 B 告诉我的，那我要去这些地方，肯定得先经过 B，所以距离要加 1。”
        
2. **“对比与更新”：** A 拿出“加工”后的表，跟自己原来的表逐条比对。
    
    - **情况 1：新路线！** 原表中没有这个目的网络 $\rightarrow$ **直接添加**。
        
    - **情况 2：同路更短！** 原表有，且新路线跳数更少 $\rightarrow$ **更新**（换成更短的路）。
        
    - **情况 3：同路更长，但来源相同！** 原表有，下一跳也是 B，但现在跳数变大了 $\rightarrow$ **必须更新！**
        
        - _🚨 考研高频坑点：_ 为什么变长了也要更新？因为下一跳是 B，说明这条路原本就是依靠 B 的。现在 B 说“涨价了”（路变远了），A 只能捏着鼻子认了，说明网络拓扑变了。
            
    - **情况 4：同路更长，来源不同。** 原表有，下一跳是 C，且距离比 B 提供的短 $\rightarrow$ **不更新**（我有更好的路，不听 B 的）。
        

#### 🧮 举个栗子（考研真题模式）

A 的原路由表：

| 目的网 | 下一跳 | 距离 |
| :--- | :--- | :--- |
| N1 | C | 2 |
| N2 | C | 4 |

A 收到 B 发来的路由表（原始数据）：

| 目的网 | 距离 |
| :--- | :--- |
| N1 | 4 |
| N2 | 2 |
| N3 | 1 |

**👉 第一步：A 对 B 的表进行“加工”（距离+1，下一跳改B）：**

- N1: 5, B
- N2: 3, B
- N3: 2, B

**👉 第二步：A 更新自己的表：**

1. **N1:** 原来是 (2, C)。新的是 (5, B)。5 > 2，且下一跳不同 $\rightarrow$ **不更新**。
    
2. **N2:** 原来是 (4, C)。新的是 (3, B)。3 < 4 $\rightarrow$ **更新！** (发现了捷径)。
    
3. **N3:** 原来没有 $\rightarrow$ **添加！**
    

👉 A 的最终路由表：

| 目的网 | 下一跳 | 距离 |
| :--- | :--- | :--- |
| N1 | C | 2 |
| N2 | B | 3 |
| N3 | B | 2 |

### 3. 致命弱点：坏消息传得慢 (Count-to-Infinity)

RIP 最著名的缺点就是**慢收敛**，容易产生路由环路。这在考研中常以简答题出现。

#### 场景模拟

设想网络：`A --1-- B --1-- C` (A 到 C 距离是 2)。

1. 突然，**C 断网了**。
    
2. B 检测到 C 不可达，把到 C 的距离改为 **16**。
    
3. **但是！** 在 B 把这个“坏消息”告诉 A 之前，A 先把自己的“旧新闻”告诉了 B：“嘿，B，我知道怎么去 C，距离是 2，下一跳是你。”
    
4. B 一听：“哎？A 能去 C？那我把包给 A 岂不是距离 3 就到了？”（B 忘了这消息其实是自己当年告诉 A 的）。于是 B 更新表：到 C 距离 3，下一跳 A。
    
5. A 收到 B 的更新：“哦，B 到 C 变成 3 了？那我经由 B 去就是 4。”
    
6. **循环开始：** 3...4...5...6... 直到 **16**。
    

这就是 **“好消息传得快，坏消息传得慢”**（计数到无穷大问题）。

---

### 4. 解决方案（必背术语）

为了解决上面那个愚蠢的循环，RIP 引入了三个补丁：

1. **水平分割 (Split Horizon):**
    
    - **原理：** 从接口 X 收到的路由信息，**不再**从接口 X 发回。
        
    - _通俗解释：_ B 告诉 A 的消息，A 闭嘴不回传给 B。这能阻止基本的环路。
        
2. **毒性逆转 (Poison Reverse):**
    
    - **原理：** 从接口 X 收到的路由信息，我**要**发回给接口 X，但是把距离设置为 **16**（不可达）。
        
    - _通俗解释：_ A 明确告诉 B：“别指望我，我对那条路是死路。”（比水平分割更狠，效果更好）。
        
3. **触发更新 (Triggered Update):**
    
    - **原理：** 一旦网络拓扑变动，**不等 30 秒**，立刻发送更新报文。
        
    - _作用：_ 加速收敛，减少产生环路的概率。

### 5. RIPv1 vs RIPv2（做题要看清）

考研选择题如果不标注，默认讲 RIP 机制；但如果有具体协议对比：

| **特性**   | **RIPv1**            | **RIPv2**           |
| -------- | -------------------- | ------------------- |
| **寻址方式** | 广播 (255.255.255.255) | **组播 (224.0.0.9)**  |
| **子网掩码** | **不支持** (分类编址)       | **支持** (VLSM, CIDR) |
| **安全性**  | 无身份验证                | 支持简单的明文/MD5认证       |
## 功能网络&实现应用
RIP 从**功能**上讲确实是**网络层**协议（因为它负责路由，服务于网络层），但从**实现**上讲，它又是运行在**应用层**的（因为它像一个普通应用程序一样使用 UDP 端口 520 进行通信）。

为了帮你彻底理清这个逻辑，我们可以把它拆解为三个层次来理解：

### 1. 核心矛盾：功能 vs. 实现

我们判断一个协议属于哪一层，通常有两个标准，而 RIP 正好在这两个标准上“精神分裂”了：

- **标准 A：它为谁服务？（功能视角）**
    
    - RIP 的作用是计算路由表，帮助路由器转发 IP 数据包。
        
    - 它的工作结果（路由表）是直接给网络层（IP 协议）使用的。
        
    - **结论：** 它是**网络层**协议。
        
- **标准 B：它被谁封装？（实现视角）**
    
    - RIP 没有自己独立的传输机制，它不想自己去处理数据包的校验、分用等繁琐工作。
        
    - 所以，它选择“寄生”在 UDP 协议之上。RIP 的报文是装在 UDP 数据报里的（端口号 520）。
        
    - 在操作系统中（比如 Linux），RIP 通常就是一个运行在用户空间的**守护进程（daemon）**，这就跟 HTTP、FTP 这些应用层软件长得一模一样。
        
    - **结论：** 它是**应用层**协议。
        

### 2. 为什么 RIP 要用 UDP（传输层）？

你可能会问：“既然它是搞路由的，为什么不直接像 OSPF 那样封装在 IP 包里，非要多套一层 UDP？”

原因在于 **“偷懒”**（或者说是设计的**简单性**）：

- **开发简单：** RIP 是非常古老的协议。当时的设计者为了省事，不想在 RIP 协议里重新写一套“如何发送数据、如何校验数据”的代码。
    
- **利用现成工具：** UDP 已经提供了端口号（可以区分程序）和校验和（保证数据不出错），RIP 直接拿来用最方便。
    
- **对比 OSPF：** OSPF 为了追求极致的效率和控制，自己定义了传输规则，直接封装在 IP 包中（协议号 89），没有用 TCP 或 UDP。所以 OSPF 看起来更像“纯正”的网络层协议。
    

### 3. 考研/考试标准答案

在考研（408）或大多数学术考试中，如果问你：

- **“RIP 属于哪一层的协议？”**
    
    - 标准答案通常是 **应用层**。
        
    - _理由：_ 因为它运行在 UDP 之上。
        
- **“RIP 是哪一层的路由协议？”**
    
    - 这时候要强调它的功能，它是为 **网络层** 服务的路由协议。
        

### 4. 路由协议“全家桶”对比（必考）

为了让你更清晰，我把三大路由协议的“靠山”列出来，一目了然：

|**协议**|**类型**|**封装/传输方式**|**端口/协议号**|**"名义"层级**|**备注**|
|---|---|---|---|---|---|
|**RIP**|距离矢量|**UDP**|端口 520|**应用层**|最“省事”，借用 UDP|
|**OSPF**|链路状态|**IP**|协议号 89|**网络层**|最“独立”，直接坐 IP 上|
|**BGP**|路径矢量|**TCP**|端口 179|**应用层**|最“稳重”，借用 TCP|
## 注意点
#怎么分层
**在 TCP/IP 模型中，谁被谁包裹（封装），谁就在谁的上面。**

### 1. 为什么“用 UDP” = “应用层”？

- **UDP 是那一层？** -> **运输层 (Transport Layer)**。
    
- **RIP 在哪里？** -> RIP 的数据是**塞在 UDP 的肚子里**传走的。
    

既然 RIP 是 UDP 的“乘客”，那 RIP 的地位就必须比 UDP 高一级。

UDP 是第 4 层，那坐在它上面的 RIP 自然就是 第 5 层（应用层）。

### 2. 看个解剖图就明白了

想象一下一个 RIP 数据包在网线上传输时的样子（报文结构）：

$$\text{[ 以太网首部 [ IP 首部 [ \textbf{UDP 首部} [ \textbf{RIP 报文} ] ] ] ]}$$

- **IP** 负责把车开到目的地（网络层）。
    
- **UDP** 负责把货物交到 520 号柜台（运输层）。
    
- **RIP** 是柜台里那个具体的货物（应用层）。
    

**类比一下：**

- **HTTP** 用 TCP（运输层），所以 HTTP 是**应用层**。
    
- **DNS** 用 UDP（运输层），所以 DNS 是**应用层**。
    
- **RIP** 用 UDP（运输层），所以 RIP 也是**应用层**。
    

### 3. 为什么你觉得它应该是运输层？

你可能觉得：“RIP 是用来辅助数据传输路由的，应该属于运输系统的一部分啊？”

**纠正观念：**

- **运输层 (Transport Layer)** 的核心职责是 **“端到端的数据传输管道”**（不管传的是什么）。
    
- **RIP** 并不负责建立管道，它只是利用现成的 UDP 管道，去**聊天**（交换路由信息）。
    

它就像是一个**普通的应用程序**（比如你写的 Java 程序），只是它聊天的内容比较特殊（聊的是路由表），而且它占用了系统保留的 **520 端口**。
