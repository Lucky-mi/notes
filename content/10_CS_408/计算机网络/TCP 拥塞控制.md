简单概括：
慢开始指数增长，到门限值以后线性增长（当然都是以RTT为单位）；超时之后门限值等于此时的拥塞窗口的一半，然后从慢开始开始，如果收到3个冗余确认，则快恢复，直接从新门限值开始拥塞线性增长（新门限值也是冗余确认时拥塞窗口的一半）
## 1. 核心概念与前提

### 1.1 拥塞控制 vs. 流量控制

- **流量控制**：点对点（接收方限制发送方），依据 `rwnd`。
    
- **拥塞控制**：全局性（整个网络环境限制发送方），依据 `cwnd`。
    
- 发送方最终窗口：
    
    $$发送窗口 = \min(\text{rwnd}, \text{cwnd})$$
    
    (注：做拥塞控制题目时，通常假设接收方缓存无限大，即忽略 rwnd，只看 cwnd)
    

### 1.2 两个核心变量

1. **cwnd (Congestion Window，拥塞窗口)**：发送方维护的一个状态变量，其值取决于网络的拥塞程度，并动态变化。单位通常是 **MSS (最大报文段长度)**。
    
2. **ssthresh (Slow Start Threshold，慢开始门限)**：决定何时从“慢开始”阶段切换到“拥塞避免”阶段的阈值。
    

### 1.3 拥塞的判断标准

TCP 认为只要出现 **“丢包”**，就意味着网络出现了拥塞。

- **丢包的两种表现**：
    
    1. **超时 (Timeout)**：重传计时器到期（严重拥塞）。
        
    2. **收到 3 个重复的 ACK**：说明有个别报文丢失，但网络尚可通信（轻度拥塞）。
        

---

## 2. 四大核心算法详解

TCP 的拥塞控制算法发展经历了 TCP Tahoe (旧版本) 和 TCP Reno (当前主流/考研标准) 两个阶段。**考研主要考察 TCP Reno 版本（包含快重传和快恢复）。**

### 2.1 慢开始 (Slow Start)

**误区提示**：“慢”并不是指增长慢，而是指**初始起点低**（从 1 开始），实际上增长速度非常快（指数增长）。

- **条件**：`cwnd < ssthresh`
    
- **初始值**：`cwnd = 1` (1个 MSS)。
    
- **增长规则**：
    
    - **每收到一个** 对新报文段的确认 ACK，`cwnd` 加 1。
        
    - **每经过一个传输轮次 (RTT)**，`cwnd` **加倍** ($1 \rightarrow 2 \rightarrow 4 \rightarrow 8 \dots$)。
        
- **结束条件**：当 `cwnd` 达到 `ssthresh` 时，改用拥塞避免算法。
    

> [!NOTE] 细节计算
> 
> 如果 cwnd 翻倍后超过了 ssthresh，则下一次 cwnd 取 ssthresh 的值。
> 
> 例如：ssthresh=12, cwnd=8。下一轮 cwnd 理论是 16，但只能取 12。

### 2.2 拥塞避免 (Congestion Avoidance)

- **条件**：$cwnd \ge ssthresh$
    
- **增长规则**：**加法增大 (Additive Increase)**。
    
    - 每经过一个 RTT，`cwnd` 增加 1 ($+1$)。
        
    - 不再指数增长，而是线性增长，为了小心翼翼地探测网络极限。
        

### 2.3 快重传 (Fast Retransmit)

**目的**：让发送方尽早知道发生了个别报文段丢失，避免超时重传（超时会导致重回慢开始，代价太大）。

- **触发机制**：接收方发现收到的报文段序号不连续（比如收到了 M1, M2, M4，缺 M3），接收方会立即重复发送对 M2 的确认（即 ACK=3，期待收到3）。
    
- **动作**：当发送方一连收到 **3 个重复的 ACK** (3 Duplicate ACKs) 时，立即重传丢失的报文段 M3，而不需要等待 M3 的计时器超时。
    

### 2.4 快恢复 (Fast Recovery) - **Reno 版本的核心**

当触发“快重传”时，发送方认为网络只是“轻度拥塞”（毕竟还能收到 3 个 ACK，说明后续报文到了），因此**不执行**严重的“超时处理”（不回滚到 1）。

- **触发条件**：收到 3 个重复 ACK。
    
- **算法调整步骤**：
    
    1. **调整门限**：`ssthresh = cwnd / 2` (当前窗口的一半)。
        
    2. **调整窗口**：`cwnd = ssthresh` (注意：有的实现是 ssthresh + 3，考研通常按等于新的 ssthresh 计算，或者题目会指定)。
        
    3. **进入阶段**：直接进入 **拥塞避免** 阶段（执行线性增长）。
        

---

## 3. 拥塞窗口变化全过程图解 (考研重点)

这是 408 大题中最喜欢考的折线图分析。我们将情况分为 **超时** 和 **3个重复ACK** 两种路径。

### 3.1 路径 A：发生超时 (Timeout) - 严重拥塞

这是 TCP Tahoe 的处理方式，也是 TCP Reno 在极端情况下的保底策略。

1. **现象**：发送方迟迟收不到确认，计时器超时。
    
2. **惩罚**：
    
    - `ssthresh` 设为当前 `cwnd` 的一半。
        
    - `cwnd` **重置为 1**。
        
    - 重新进入 **慢开始**。
        
    - _口诀：一夜回到解放前。_
        

### 3.2 路径 B：收到 3 个重复 ACK - 轻度拥塞 (快恢复)

这是 TCP Reno 的标志性特征。

1. **现象**：收到 3 个重复 ACK。
    
2. **调整**：
    
    - `ssthresh` 设为当前 `cwnd` 的一半。
        
    - `cwnd` 设为新的 `ssthresh` 值。
        
    - 直接进入 **拥塞避免** (线性增长)。
        
    - _口诀：乘法减小，加法增大 (AIMD)。_
        

---

## 4. 实例演算 (建议手抄一遍)

**假设**：TCP 连接处于拥塞避免阶段，当前 `cwnd = 24`，`ssthresh = 16`。

### 场景一：发生超时 (Timeout)

1. **事件**：发生超时。
    
2. **参数更新**：
    
    - `ssthresh_new = 24 / 2 = 12`
        
    - `cwnd_new = 1`
        
3. **后续走势 (按 RTT 轮次)**：
    
    - RTT 1: `cwnd` = 1 (慢开始)
        
    - RTT 2: `cwnd` = 2
        
    - RTT 3: `cwnd` = 4
        
    - RTT 4: `cwnd` = 8
        
    - RTT 5: `cwnd` = 12 (到达 ssthresh_new，停止指数增长)
        
    - RTT 6: `cwnd` = 13 (拥塞避免，线性增长)
        

### 场景二：收到 3 个重复 ACK (快恢复)

1. **事件**：收到 3 个重复 ACK。
    
2. **参数更新**：
    
    - `ssthresh_new = 24 / 2 = 12`
        
    - `cwnd_new = 12` (直接等于新的 ssthresh)
        
3. **后续走势 (按 RTT 轮次)**：
    
    - RTT 1: `cwnd` = 12 (从这里开始)
        
    - RTT 2: `cwnd` = 13 (拥塞避免，线性增长)
        
    - RTT 3: `cwnd` = 14

## 5. 考研常考“坑点”总结

> [!IMPORTANT] 必须记住的规则
> 1. **慢开始的转折点**：
> - 若 `cwnd` 加倍后正好等于 `ssthresh`，下个 RTT 开始线性增长。
> - 若 `cwnd` 加倍后会超过 `ssthresh`，则下个 RTT 的 `cwnd` 限制为 `ssthresh`，之后开始线性增长。
> 2. **传输轮次 (RTT) vs. 确认次数**：
> - 题目如果问“经过第 N 个 RTT 后，cwnd 是多少”，指的是一轮结束后的状态。
> - 慢开始阶段，**每收到一个 ACK**，cwnd + 1。这意味着一个 RTT 内，cwnd 会翻倍（发送 k 个，回 k 个 ACK，加 k，即 $k+k=2k$）。
> 3. **最小门限值**：
> - `ssthresh` 减半时，如果计算结果小于 2，通常取 2 (具体看题目设定，一般不考这么细，但要知道不能为 0)。
> 1. **发送量的计算**：
> - 题目可能会问“前 N 个 RTT 共发送了多少数据？”
> - **解法**：把每个 RTT 的 `cwnd` 值加起来即可 (假设发送窗口等于拥塞窗口)。
> - 例如：1 + 2 + 4 + 8 + 12 ...
        
# TCP 拥塞控制疑难解析：快重传机制细节

> 适用场景：考研 408 难点辨析、面试深挖
> 
> 核心问题：为什么是 3 次重复确认？快重传是默认开启的吗？

## 1. 为什么必须是 3 次重复 ACK？(Why 3 Duplicate ACKs?)

这个数字不是拍脑袋定的，而是为了在 **“网络乱序”** 和 **“数据丢失”** 之间寻找一个平衡点。

### 1.1 核心矛盾：乱序 vs 丢包

TCP 需要区分两种情况：

1. **丢包 (Packet Loss)**：报文段真的在网络中消失了（路由器丢弃）。
    
2. **乱序 (Reordering)**：报文段没丢，只是因为网络路径不同，后发的报文先到了，先发的报文在路上。
    

**如果一收到重复 ACK 就重传（即 1 次重复 ACK 就重传）：**

- 只要网络稍微出现一点乱序（比如报文 2 比报文 3 晚到了 1ms），发送方就会误以为报文 2 丢了，立即重传。
    
- **后果**：由于互联网中乱序非常常见，这会导致大量的**无效重传**，浪费带宽。
    

### 1.2 "3次" 的数学逻辑

根据 TCP 的设计者（Van Jacobson 等人）的经验数据和概率分析：

- **收到 1-2 个重复 ACK**：很有可能是**乱序**造成的。
    
    - _场景_：发送 1, 2, 3, 4, 5。2 只是晚了一点点，3 和 4 先到了。接收方收到 3 和 4 时会发两个针对 1 的重复 ACK。此时 2 到了，不需要重传。
        
- **收到 3 个重复 ACK**：乱序造成的概率极小，**丢包**的概率极大。
    
    - _逻辑_：如果接着收到了 3 个后续报文（触发了 3 次重复 ACK），说明网络不仅能通，而且还很顺畅地传输了 3 个包，唯独那个缺口的包一直没来。这时候大概率是真的丢了。
        

> [!NOTE] 考研必记结论
> 
> - **重复 ACK < 3**：TCP 倾向于认为是**乱序**，暂不重传，继续等待。
>     
> - **重复 ACK = 3**：TCP 判定为**丢包**，立即触发**快重传**。
>     

---

## 2. 快重传是始终存在的机制吗？

### 2.1 这里的“始终存在”指什么？

这取决于你使用的 TCP **版本（拥塞控制算法）**。

### 2.2 版本演变 (考研视角)

1. **TCP Tahoe (旧版本)**：
    
    - **没有快恢复**。
        
    - 有快重传，但是快重传后，它会把 `cwnd` 置为 1，重新进入**慢开始**。
        
2. **TCP Reno (考研标准版)**：
    
    - **默认包含** 快重传 + 快恢复。
        
    - 在 408 考试和大多数教科书中，当我们讨论现代 TCP 时，**默认认为快重传和快恢复是标准配置，是始终生效的逻辑**。
        

### 2.3 实际操作系统 (扩展知识)

在真实的 Linux 或 Windows 系统中，TCP 的拥塞控制算法是可以切换的（如 Cubic, BBR, Reno）。

- **绝大多数现代算法 (Reno, Cubic 等)**：都包含快重传机制。
    
- **是否需要协商？**：不需要。这是发送方自己的算法逻辑，不需要在三次握手时像“窗口扩大因子”那样进行协商。只要发送方采用了支持快重传的算法，它就会执行。
    

> [!IMPORTANT] 总结
> 
> - **在考研中**：请默认快重传是 TCP 的**固有机制**，无需特殊条件激活，只要满足“3 个重复 ACK”就会触发。
>     
> - **例外**：除非题目明确说“假设该连接使用 TCP Tahoe 版本”或者“不使用快重传机制”。
>     

---

## 3. 图解：究竟发了多少个 ACK？

很多同学数不清楚到底发了几个 ACK，这里详细拆解一下。

假设发送方发送：M1, M2, M3, M4, M5

情况：M2 丢失了

| **动作** | **接收方收到的数据**  | **接收方发送的确认 (ACK)**    | **说明**                        |
| ------ | ------------- | --------------------- | ----------------------------- |
| **正常** | 收到 M1         | **ACK = 2** (期待 M2)   | 正常的确认                         |
| **异常** | 收到 M3 (M2 没来) | **ACK = 2** (还是期待 M2) | **第 1 个重复 ACK** (冗余 ACK)      |
| **异常** | 收到 M4         | **ACK = 2**           | **第 2 个重复 ACK**               |
| **异常** | 收到 M5         | **ACK = 2**           | **第 3 个重复 ACK** -> **触发快重传！** |

- **总共收到了**：1 个正常 ACK + 3 个重复 ACK = 4 个 ACK。
    
- **触发点**：是计算 **“重复的”** 那一类，满 3 个就触发。

# 深度解析：拥塞崩溃 (Congestion Collapse)

> 适用场景：传输层协议设计原理、网络性能优化、Linux 内核网络调优
> 
> 核心问题：为什么没有拥塞控制，网络会陷入“死锁”状态？

## 1. 现象定义：什么是拥塞崩溃？

你所说的“死锁”，在宏观网络上表现为：

链路利用率 (Throughput) 可能高达 100%，但有效吞吐量 (Goodput) 却趋近于 0。

- **直观理解**：高速公路上塞满了车（带宽占满），但所有的车都在原地不动或者刚刚开上去就被赶下来（丢包），没有任何一辆车能抵达终点。
    
- **历史背景**：这不是理论推演，而是 1986 年 10 月发生在 NFSnet（互联网前身）的真实灾难。当时从 LBL 到 UC Berkeley 的连接速度从 32 Kbps 骤降到 40 bps（降低了 1000 倍），网络实际上“死”了。
    

## 2. 产生机制：正反馈循环 (Positive Feedback Loop)

这是你最需要理解的**细节**。拥塞崩溃之所以可怕，是因为它是一个**恶性循环**。

假设 TCP **没有**拥塞控制（即没有慢开始、没有拥塞避免，丢包后依然全速重传）：

1. **初始拥塞**：网络中某个路由器节点的缓存队列满了，开始丢弃报文。
    
2. **超时重传**：发送方 A 的 TCP 发现超时（ACK 没回来），因为它没有拥塞控制逻辑，它认为是偶尔的错误，于是**立即**重传数据，甚至发送更多新数据。
    
3. **加剧拥塞**：这些“重传包”和“新数据包”再次涌向那个已经堵死的路由器。
    
4. **无效带宽消耗 (核心死锁点)**：
    
    - 路由器为了处理这些重传包，消耗了带宽和 CPU。
        
    - 但是因为队列还是满的，这些包在传输了一段距离后，**再次被丢弃**。
        
    - **重点**：报文在到达瓶颈路由器之前，已经占用了上游链路的带宽。一旦被丢弃，上游链路刚才做的传输工作全部变成“无效功”。
        
5. **循环崩溃**：
    
    - 丢包越多 $\rightarrow$ 发送方重传越猛 $\rightarrow$ 网络负载越重 $\rightarrow$ 丢包更多。
        
    - 最终，整个网络充斥着大量的**重传副本**，但没有一个副本能完整到达目的地。
        

> [!IMPORTANT] 关键区别：Throughput vs. Goodput
> 
> - **Throughput (吞吐量)**：单位时间内通过网络的数据量（包含重传的废包）。在崩溃时，这个值可能很大。
>     
> - **Goodput (有效吞吐量)**：单位时间内应用层成功收到的不重复数据量。在崩溃时，这个值归零。
>     
> - **死锁本质**：$\text{Throughput} \approx \text{Capacity}$，但 $\text{Goodput} \approx 0$。
>     

---

## 3. 深度延展：另一个层面的“死锁”——全局同步 (Global Synchronization)

除了完全没有拥塞控制导致的崩溃，还有一种情况发生在使用早期 TCP（如 TCP Tahoe）配合简单的路由器策略（尾部丢弃 Tail Drop）时。

这也算是一种“震荡型死锁”。

- **现象**：
    
    1. 网络中有 1000 个 TCP 连接。
        
    2. 路由器缓存满了，采用**尾部丢弃**策略（谁后来的我丢谁）。
        
    3. 结果导致大量连接**同时**检测到丢包。
        
    4. 这 1000 个连接**同时**进入慢开始（cwnd=1）。
        
    5. 网络流量瞬间断崖式下跌（链路空闲）。
        
    6. 所有连接又**同时**开始指数增长。
        
    7. 网络流量瞬间打满，再次同时丢包。
        
- **结果**：网络利用率呈现剧烈的“锯齿状”波动，平均利用率很低，这也是一种广义上的效率“死锁”。
# 网络层与传输层的跨层协作：AQM 与 RED 算法详解

> 适用场景：考研 408 网络层拥塞控制策略、高级网络工程师面试
> 
> 核心逻辑：路由器不再是被动的“水桶”，而是主动的“交通指挥官”。

## 1. 传统策略的弊端：尾部丢弃 (Tail Drop)

在 AQM 出现之前，路由器处理排队分组的策略非常简单粗暴，叫做 **尾部丢弃 (Tail Drop)**。

- **机制**：路由器的缓存就是一个有限的队列。当队列**填满**时，后续到达的所有分组（无论属于哪个 TCP 连接）全部丢弃。
    
- **后果**：这就是导致**全局同步 (Global Synchronization)** 的元凶。
    
    1. **并发丢包**：当队列满时，可能正好有 100 个 TCP 连接的数据包同时到达。
        
    2. **并发减速**：这 100 个 TCP 发送方几乎同时检测到丢包（或者超时），同时触发拥塞控制（cwnd 减半或归 1）。
        
    3. **并发恢复**：网络负载瞬间骤降，链路空闲。随后这 100 个连接又同时开始慢开始/拥塞避免，流量猛增。
        
    4. **震荡**：网络利用率像心电图一样剧烈波动，不仅浪费带宽，还增加了抖动。
        

---

## 2. AQM 的核心：RED (随机早期检测)

**AQM 的哲学**：不要等“撞墙”（队列满）了再刹车，而是在快要撞墙时，提前提醒个别车辆减速。

### 2.1 RED 算法的工作流程

RED 算法通过监控**平均队列长度 ($L_{avg}$)** 来决定是否丢包。它设置了两个门限：**最小门限 ($Th_{min}$)** 和 **最大门限 ($Th_{max}$)**。

1. **正常状态 ($L_{avg} < Th_{min}$)**：
    
    - 队列很空，网络畅通。
        
    - **动作**：不丢包，正常转发。
        
2. **随机丢包状态 ($Th_{min} < L_{avg} < Th_{max}$)** —— **核心区域**
    
    - 队列开始积压，但这可能只是暂时的突发，也可能是拥塞的前兆。
        
    - **动作**：按照一个**概率 $P$** 随机丢弃到达的分组。
        
    - **关键细节**：队列越长（越接近 $Th_{max}$），丢弃概率 $P$ 就越大（线性增加）。
        
3. **拥塞状态 ($L_{avg} > Th_{max}$)**：
    
    - 队列已经非常危险了。
        
    - **动作**：丢弃所有到达的分组（退化为尾部丢弃）。
        

### 2.2 为什么“随机丢包”能解决问题？(回答你的疑惑)

回到你的问题：**“随机丢弃难道不是也会造成重传吗？”**

**答案是：是的，会造成重传。但我们要的就是这个重传！**

RED 的精妙之处在于**“去同步化” (Desynchronization)**：

1. **点杀而非扫射**：
    
    - 在队列还没满时，RED 随机挑了一个倒霉蛋（比如连接 A 的一个包）丢掉了。
        
    - 此时，**只有连接 A** 会检测到丢包，从而将其 `cwnd` 减半，降低发送速率。
        
    - 其他的 99 个连接（连接 B, C, D...）完全不知情，继续全速发送。
        
2. **软着陆**：
    
    - 连接 A 减速后，让出了带宽，缓解了路由器的排队压力。
        
    - 如果队列还在增长，RED 再随机丢掉连接 B 的一个包，让 B 也减速。
        
    - **结果**：所有的 TCP 连接是**轮流减速**，而不是**同时减速**。
        
3. **宏观效果**：
    
    - 虽然微观上每个连接都在经历“丢包-重传-减速”，但宏观上，总的流量保持在链路容量附近，非常平稳，没有剧烈的“锯齿”波动。
        

> [!NOTE] 考研/面试 必杀技
> 
> RED 利用了 TCP 的拥塞控制机制作为反馈回路。它通过制造轻微的丢包（TCP 收到 3 个重复 ACK，触发快重传/快恢复），来避免严重的丢包（队列溢出导致超时 RTO）。
> 
> - **代价**：少量的重传。
>     
> - **收益**：避免了全局同步，降低了平均延迟（因为队列不会一直维持在满的状态）。
>     

---

## 3. RED 的缺陷与进化

虽然 RED 解决了全局同步，但它也有问题（考研可能作为选择题干扰项出现）：

1. **参数难调**：$Th_{min}$, $Th_{max}$, $P_{max}$ 很难设置。设得不好，要么太迟钝（退化为尾部丢弃），要么太敏感（带宽利用率低）。
    
2. **对 UDP 不公平**：
    
    - 如果网络里有一个 UDP 流（不响应拥塞控制），RED 丢它的包，它根本不在乎，继续猛发。
        
    - TCP 响应丢包减速了。
        
    - 结果：UDP 占满了缓冲区，RED 只能拼命丢 TCP 的包。

# ECN (显式拥塞通知)

### 1.1 考研考察程度

- **结论**：ECN 属于 **“大纲边缘但教材中有”** 的知识点。
    
- **地位**：在谢希仁《计算机网络》和 Kurose 的《自顶向下》中均有介绍。
    
    - **408 统考**：极少直接考 ECN 的原理大题，通常不会让你画图。
        
    - **选择题**：可能会作为干扰项出现，或者考查“TCP/IP 首部中哪些字段支持拥塞控制”。
        
    - **复试/面试**：这是一个加分项，表明你关注新技术。
        

### 1.2 ECN 的原理：打标记，不丢包

刚才讲的 AQM/RED 是通过“杀鸡儆猴”（丢包）来通知发送方。而 ECN 是“贴条警告”。

1. **IP 层协作 (路由器)**：
    
    - IP 首部有一个 **ToS (服务类型)** 字段（现称为 DS 字段）。
        
    - 当路由器发现队列快满了（拥塞），它不丢包，而是把 IP 首部中的 **ECN 位** 设为 1（打上标记）。
        
2. **传输层协作 (TCP)**：
    
    - **接收方**收到带标记的 IP 包，发现“哦，路由器在喊挤了”。
        
    - 接收方在给发送方回 ACK 时，把 TCP 首部的 **ECE (ECN-Echo)** 标志位设为 1。
        
    - **发送方**收到 ECE=1 的 ACK，知道网络拥塞了，主动把 `cwnd` 减小（就像发生了快重传一样）。
        
    - 发送方下次发送报文时，把 TCP 首部的 **CWR (Congestion Window Reduced)** 设为 1，告诉接收方“我已经减速了，别喊了”。

#  核心辨析：超时 vs. 3个重复ACK

你问了一个非常深刻的问题：**“超时不是ack重复确认也能表现的吗？”**

**答案是：绝对不能。这两者在 TCP 眼里是完全互斥的两种状态。**

这是理解“慢开始”和“快恢复”触发条件区别的关键。

### 2.1 本质区别：死寂 vs. 嘈杂

#### A. 超时 (Timeout) = “死一般的寂静”

- **场景**：发送方发了数据包 M1。
    
- **现象**：
    
    - 网络彻底断了，或者极度拥塞。
        
    - M1 没到接收方，或者接收方回的 ACK 也没回来。
        
    - 发送方在 RTO（重传计时器）的时间内，**连一个屁都没收到**（既没有正常的 ACK，也没有重复的 ACK）。
        
- **推断**：网络可能瘫痪了，连个回音都没有。这是**最严重**的拥塞。
    
- **动作**：**核打击**。
    
    - `ssthresh` 减半。
        
    - `cwnd` **直接归 1**。
        
    - 进入**慢开始**。
        

#### B. 3个重复ACK (3 Duplicate ACKs) = “吵闹的抱怨”

- **场景**：发送方发了 M1, M2, M3, M4, M5。M2 丢了。
    
- **现象**：
    
    - 接收方收到了 M3, M4, M5。
        
    - 接收方很诚实，每收到一个包就喊一次：“我收到后面的了，但我还是缺 M2！(ACK=2)”。
        
    - 发送方连续收到了 3 次这种“抱怨”。
        
- **推断**：
    
    - 既然能收到 3 个重复 ACK，说明 **网络是通的**！
        
    - 后续的包（M3, M4, M5）都顺利穿过路由器到达了接收方。
        
    - 仅仅是 M2 运气不好丢了。网络只是**轻度拥塞**。
        
- **动作**：**软着陆**。
    
    - `ssthresh` 减半。
        
    - `cwnd` **减半** (等于新的 ssthresh)。
        
    - 进入**拥塞避免** (快恢复)。

|**特性**|**超时 (Timeout)**|**3个重复 ACK**|
|---|---|---|
|**收到的反馈**|**无** (时间到了都没动静)|**有** (连续收到 3 个特定的 ACK)|
|**网络状况推断**|**严重拥塞/中断** (路断了)|**个别丢失** (车能过，偶尔掉货)|

# 3. 为什么“超时”不能用“重复ACK”表现？

为了彻底消除你的疑虑，我们模拟一下：

- **如果发生了超时**：意味着发送方发出去的包，或者回来的 ACK，**全部**死在了路上。发送方根本收不到任何 ACK，更别提“重复”的 ACK 了。
    
- **只要能收到重复 ACK**：就证明链路还是**活**的，既然是活的，计时器就不会空转到超时（因为每收到一个 ACK，虽然是重复的，但也证明了连通性）。

# TCP 拥塞控制的基石：AIMD (加法增大乘法减小) 深度剖析

> 适用场景：考研 408 难点辨析、网络性能分析、算法设计
> 
> 核心问题：为什么 TCP 选择了“加法增大，乘法减小”？为什么不是“加法减小”或者“乘法增大”？这背后隐藏着怎样的数学收敛性？

## 1. AIMD 的控制方程

在 **拥塞避免 (Congestion Avoidance)** 阶段，TCP 的窗口调整遵循以下线性控制方程：

1. **AI (Additive Increase - 加法增大)**：
    
    - **场景**：收到一个 ACK（网络无拥塞）。
        
    - **公式**：$cwnd \leftarrow cwnd + \alpha$ (通常 $\alpha = 1 \text{ MSS}/RTT$)
        
    - **表现**：线性增长，斜率为 1。
        
2. **MD (Multiplicative Decrease - 乘法减小)**：
    
    - **场景**：发生拥塞（检测到丢包）。
        
    - **公式**：$cwnd \leftarrow cwnd \times (1 - \beta)$ (通常 $\beta = 0.5$)
        
    - **表现**：指数级下跌，瞬间减半。
        

---

## 2. 两个终极目标：效率 vs. 公平

要理解 AIMD，必须先设定两个评价标准。假设网络中只有两个 TCP 用户（User 1 和 User 2）共享一条瓶颈带宽 $C$。

1. **效率 (Efficiency)**：
    
    - 网络的带宽应该被用满，不浪费。
        
    - 数学表达：$x_1 + x_2 = C$ (两人的速率之和等于总带宽)。
        
2. **公平 (Fairness)**：
    
    - 每个人分到的带宽应该大致相等。
        
    - 数学表达：$x_1 = x_2$。
        

---

## 3. 为什么必须是 AIMD？(Chiu-Jain 相图分析)

这是计算机网络理论中最经典的**矢量相图 (Phase Plot)** 分析。我们将 User 1 的带宽作为 X 轴，User 2 的带宽作为 Y 轴。

### 3.1 坐标系详解

- **效率线 (Efficiency Line)**：$x + y = C$。这条线上的点表示带宽用满了。在此线**下方**表示带宽未跑满（低效），在此线**上方**表示发生了拥塞（超载）。
    
- **公平线 (Fairness Line)**：$x = y$ (45度射线)。这条线上的点表示两人速率相等。
    
- **最优工作点 (Optimal Point)**：效率线与公平线的交点。即两人平分带宽且带宽跑满。
    

### 3.2 动态博弈过程 (收敛性证明)

假设初始状态是不公平的：User 1 占了很多带宽，User 2 占了很少 (点 A)。且 $x_1 + x_2 < C$ (还没堵)。

1. **AI 阶段 (加法增大)**：
    
    - 两人都不知道对方的存在，只是各自探测。
        
    - User 1: $x_1 + 1$; User 2: $x_2 + 1$。
        
    - **几何轨迹**：点 A 沿着 **45度方向** 向右上方移动。
        
    - **数学意义**：
        
        - 因为是在 $x_1$ 和 $x_2$ 上同时加一个常数，**由于基数不同，两者的比值 $x_1/x_2$ 实际上是在趋近于 1 的！**
            
        - _例子_：100 vs 10 (10倍差距) $\rightarrow$ 101 vs 11 (9.1倍) $\rightarrow$ 110 vs 20 (5.5倍)。
            
    - **结论**：**加法增大能被动提升公平性。**
        
2. **MD 阶段 (乘法减小)**：
    
    - 当两人的总和触碰到“效率线”（发生拥塞）时，两人同时丢包，同时执行 MD。
        
    - User 1: $0.5 x_1$; User 2: $0.5 x_2$。
        
    - **几何轨迹**：点沿着 **连接原点 $(0,0)$ 的连线** 向回缩。
        
    - **数学意义**：
        
        - 缩放不改变比值 ($x_1/x_2$ 不变)。
            
        - **它仅仅是把状态拉回非拥塞区域，并不恶化公平性。**
            
3. **循环迭代 (锯齿波的形成)**：
    
    - **AI** 把点推向右上方（改善公平性）。
        
    - **MD** 把点拉回原点方向（保持公平性）。
        
    - 经过几次 "AI $\rightarrow$ 拥塞 $\rightarrow$ MD" 的轮回，你会发现轨迹呈**螺旋状**向 **最优工作点** 收敛。
        

---

## 4. 为什么其他组合不行？

如果在考研复试中问你：“为什么不用加法减小 (AIAD)？”你可以这样秒杀全场：

|**策略组合**|**缩写**|**收敛性分析 (数学结果)**|**结果**|
|---|---|---|---|
|**加法增，加法减**|**AIAD**|不收敛。轨迹会在效率线附近震荡，但不会向公平线靠拢。谁先占了便宜，就一直占便宜。|**不公平**|
|**乘法增，加法减**|**MIAD**|发散！越不公平的情况会被放大。大流量用户增长更快 ($100 \times 1.1 > 10 \times 1.1$)。|**极度不公平**|
|**乘法增，乘法减**|**MIMD**|不收敛。保持当前的不公平比例，永远无法达到均分。|**不公平**|
|**加法增，乘法减**|**AIMD**|**唯一收敛** 到公平且高效的策略。|**完美**|

---

## 5. 为什么减小必须是“乘法” (Multiplicative)？

除了数学上的收敛性，从**工程实现**角度看，MD 也是必须的：

1. **清空队列的必要性**：
    
    - 当拥塞发生时，说明路由器队列呈指数级填满。
        
    - 如果只用“加法减小”（比如 `cwnd - 1`），对于积压成山的队列来说是杯水车薪，拥塞可能持续很长时间，导致大量丢包。
        
    - **乘法减小**（`cwnd / 2`）能瞬间释放出大量带宽，让路由器队列迅速排空，解除警报。
        
2. **避免拥塞崩溃**：
    
    - 还记得我们刚才讨论的“拥塞崩溃”吗？
        
    - MD 是对网络拥塞最强烈的敬畏。一旦发现问题，立即断崖式撤退，这是保证互联网不因过载而瘫痪的安全阀。
        

---

## 6. AIMD 的代价：锯齿波 (Sawtooth)

- **现象**：由于 AIMD 的机制，TCP 的吞吐量永远无法稳定在一条直线上，而是表现为 **锯齿状** 波动。
    
- **平均吞吐量**：
    
    - 最大值：$W$ (发生拥塞时的窗口)
        
    - 最小值：$W/2$ (MD 后的窗口)
        
    - **平均值**：$0.75 W$
        
- **启示**：TCP 永远在试探网络的底线。它就像一个蒙着眼睛的人在悬崖边缘试探，伸出一只脚（+1），没事再伸（+1），踩空了（丢包）立马缩回来一半（/2）。

# 概念纠正：慢开始 $\neq$ 加法增大

**这是一个非常普遍的误区，请务必在脑海中把它们分开！**

- **慢开始 (Slow Start)**：是 **指数增长**。
    
    - **增长方式**：$1, 2, 4, 8, 16 \dots$ (每经过一个 RTT 翻倍)。
        
    - **比喻**：像开车起步，虽然叫“慢”开始，但其实是为了从 0 迅速加速到高速状态。
        
- **拥塞避免 (Congestion Avoidance)**：才是 **加法增大 (AI)**。
    
    - **增长方式**：$16, 17, 18, 19 \dots$ (每经过一个 RTT 加 1)。
        
    - **比喻**：高速公路上小心翼翼地试探，一点点加速，防止超速（拥塞）。
        

> **记忆口诀**：慢开始不慢（指数爆炸），拥塞避免才慢（线性爬坡）。


# 计算tip
### 2. 题目没给门限值 (ssthresh) 怎么办？

这是考研题里常见的“空城计”。如果题目开头让你画图或者计算，但没告诉你初始的 `ssthresh` 是多少，处理原则如下：

#### 情况 A：题目是让描述“连接建立初期”

- **默认原则**：在 TCP 连接刚建立时，如果没有特殊说明，**`ssthresh` 默认被视为无穷大 (Infinite)** 或者 **非常大（比如 64KB/窗口上限）**。
    
- **后果**：这意味着第一轮慢开始（指数增长）会一直持续，直到网络发生拥塞（丢包）或者达到了接收方窗口的上限。
    

#### 情况 B：题目让你接着上一步算

- **继承原则**：如果题目是连贯的，当前的 `ssthresh` 是由**上一次**拥塞事件计算出来的。你必须往回找，看上一次丢包时 `cwnd` 是多少，除以 2 就是现在的门限。
    

---

### 3. “发送窗口”有用吗？（这是坑！这是坑！这是坑！）

**非常有用！这往往是最后一步计算的“天花板”。**

很多同学做题时，算 `cwnd` 算得太嗨了（指数爆炸增长），算出来 1, 2, 4, 8, 16, 32... 结果答案是 **20**。为什么？因为题目里悄悄藏了一句：“接收方通告窗口 (rwnd) 为 20”。

**请死记硬背这个核心公式：**

$$发送方实际发送窗口 (swnd) = \min [ \text{拥塞窗口 (cwnd)}, \text{接收方窗口 (rwnd)} ]$$

- **cwnd (Congestion Window)**：网络决定的。代表“路有多宽”（能不能跑快）。
    
- **rwnd (Receiver Window)**：接收方决定的。代表“仓库门口有多大”（能不能来得及收）。
    
- **swnd (Sending Window)**：你实际能发多少。
    

#### 典型考题场景：

- **题目**：慢开始阶段，cwnd 当前是 16，下一轮应该是 32。但是题目说 `rwnd = 20`。
    
- **陷阱**：问你下一轮能发多少数据？
    
- **答案**：不是 32，是 **20**。
    
- **后续**：如果网络没拥塞，`cwnd` 理论上还在涨（比如涨到 32, 64...），但你实际发送的数据量会被 **rwnd** 死死按在 **20** 这条水平线上，图画出来就是一个**平顶**。

### 4. 实战演练（综合你问的所有点）

题目模拟：

TCP 处于慢开始阶段，当前 cwnd = 16 MSS，ssthresh = 32 MSS。接收方通告窗口 rwnd = 24 MSS。

问：经过 2 个 RTT 后，发送窗口是多少？

**你的思考路径**：

1. **当前**：`cwnd = 16`。
    
    - 实际发送 = $\min(16, 24) = 16$。
        
2. **RTT+1**：因为是慢开始，`cwnd` 指数增长，16 -> 32。
    
    - **检查门限**：32 碰到了 `ssthresh`，下一次该变线性了。
        
    - **检查 rwnd**：`cwnd` 是 32，但 `rwnd` 是 24。
        
    - **实际发送**：$\min(32, 24) = \mathbf{24}$。 (注意：虽然拥塞窗口变大了，但被接收方限制住了)
        
3. **RTT+2**：进入拥塞避免（线性增长）。`cwnd` 从 32 -> 33。
    
    - **检查 rwnd**：`cwnd` 是 33，`rwnd` 还是 24。
        
    - **实际发送**：$\min(33, 24) = \mathbf{24}$。
        

结论：

如果不看 rwnd，你会算出 33；看了 rwnd，答案是 24。这就是“发送窗口”在题目中的致命作用。

---

### 总结 Checklist

1. **默认门限**：没给就是无穷大，一直倍增直到丢包。
    
2. **双重限制**：心中要有两个表，一个算 `cwnd`（网络），一个看 `rwnd`（接收方）。最终取**最小值**。
    
3. **取整**：`cwnd` 减半时如果出现 12.5，通常向下取整为 12。
