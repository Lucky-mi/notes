# TCP 可靠传输机制深度详解

> 适用场景：考研 408 计算题、大厂网络内核面试
> 
> 核心模块：序号/确认、滑动窗口细节（含收缩问题）、RTO 动态计算（Jacobson & Karn 算法）。

## 1. 可靠传输的四大支柱

TCP 所谓的“可靠”，依赖于以下四个核心机制的协同工作：

1. **校验 (Checksum)**：伪首部 + 首部 + 数据。检测比特错误。
    
2. **序号 (Sequence Number)**：解决数据**乱序**、**重复**问题。
    
    - TCP 是面向字节流的，序号是对**每一个字节**进行编号。
        
3. **确认 (Acknowledgment)**：解决**丢包**问题。
    
    - **累积确认**：TCP 只确认数据流中**至第一个丢失字节为止**的字节。
        
    - _例如_：收到 1-100, 201-300。接收方只能回 `ACK=101`。
        
4. **重传 (Retransmission)**：
    
    - 超时重传 (基于计时器)。
        
    - 快速重传 (基于 3 个重复 ACK)。

## 2. 滑动窗口详解 (Sliding Window)

### 2.1 窗口的三个指针

在发送方的缓存中，字节流被分为四部分，由三个指针界定：

1. **已发送且已确认** (Sent and Acknowledged)
    
2. **已发送但未确认** (Sent but not Acknowledged) -> **发送窗口内**
    
3. **允许发送但未发送** (Usable Window) -> **发送窗口内**
    
4. **不允许发送** (Not Usable) -> 窗口外
    

$$发送窗口 = \text{已发送未确认} + \text{允许发送未发送}$$

### 2.2 窗口的前移与变化

- **左沿 (Left Edge)**：
    
    - **动作**：只有收到**新的确认号 (ACK)** 时，左沿才向右移动（窗口合拢）。
        
    - **特性**：左沿**不可能**向左移动（因为不能撤销已确认的数据）。
        
- **右沿 (Right Edge)**：
    
    - **动作**：取决于 `ACK` 的数值和接收方通告的窗口值 `rwnd`。
        
    - **正常情况**：向右移动（窗口张开），表示允许发送更多数据。
        
    - **不动**：两种情况 ——
        
        1. 没有收到新 ACK，且 `rwnd` 不变。
            
        2. 收到新 ACK (左沿右移)，但 `rwnd` 变小了，导致右沿位置维持原状。
            

### 2.3 疑难点：窗口收缩 (Window Shrinking)

这是一个非常细节的考点。

- **定义**：**发送窗口的右沿向左移动**。
    
- **场景**：
    
    1. 接收方应用进程读取数据慢，接收缓存快满了。
        
    2. 接收方之前通告了一个较大的 `rwnd`（比如 1000）。
        
    3. 发送方根据这个 `rwnd` 发送了一些数据（比如序号 500-800）。
        
    4. 接收方突然反悔了（可能系统资源紧张），发送了一个新的报文，通告 `rwnd = 200`（相对于之前的基准）。
        
    5. 此时计算出的右沿位置比当前位置还要靠左。
        
- **后果**：
    
    - 发送方刚才发送的 500-800 字节数据，突然变成了“非法数据”（落在窗口外）。
        
    - 这会导致发送方逻辑混乱。
        
- **考研/标准规定**：
    
    - TCP 标准 (RFC 793) **强烈不建议 (Strongly Discouraged)** 这样做。
        
    - **做题原则**：除非题目明确描述了这种异常情况，否则默认**窗口右沿绝不向左移动**。
        
    - 如果接收方想让发送方暂停，应维持右沿不动，等待左沿慢慢追上来（即等待数据发完），而不是强制收缩。

## 3. 超时重传时间的选择 (RTO Calculation) - ★★★ 计算题核心

**RTO (Retransmission Time-Out)** 的设置是 TCP 中最精妙的数学问题。

- RTO 太短 $\rightarrow$ 不必要的重传 $\rightarrow$ 网络负荷增加。
    
- RTO 太长 $\rightarrow$ 丢包反应慢 $\rightarrow$ 效率降低。
    

### 3.1 核心难题：RTT 是波动的

**RTT (往返时间)** 随网络拥塞程度剧烈波动，因此 RTO 不能是定值，必须动态计算。

### 3.2 经典方法：加权平均往返时间 (RFC 793)

早期 TCP 使用简单的加权平均：

$$RTT_S = (1 - \alpha) \times (\text{旧 } RTT_S) + \alpha \times (\text{新 } RTT样本)$$

- $\alpha$ 推荐值为 0.125 (1/8)。
    
- **缺陷**：当 RTT 波动很大时，这个均值无法反应波动的范围，容易导致误判。
    

### 3.3 现代标准：Jacobson 算法 (考研必背公式)

Jacobson 引入了 **RTT 的偏差 (Deviation)**，类似于统计学中的“标准差”，用来衡量网络的抖动情况。

步骤 1：计算平滑 RTT ($RTT_S$)

$$RTT_S = (1 - \alpha) \times (\text{旧 } RTT_S) + \alpha \times (\text{新 } RTT样本)$$

- **标准系数**：$\alpha = 0.125$ ($1/8$)
    

步骤 2：计算 RTT 偏差 ($RTT_D$)

$$RTT_D = (1 - \beta) \times (\text{旧 } RTT_D) + \beta \times |RTT_S - \text{新 } RTT样本|$$

- **标准系数**：$\beta = 0.25$ ($1/4$)
    
- _注意：这里是绝对值，计算当前的预估值和实际采样值的差距。_
    

步骤 3：计算 RTO

$$RTO = RTT_S + 4 \times RTT_D$$

- **为什么是 4 倍？** 根据切比雪夫不等式等统计规律，覆盖 4 倍偏差范围可以保证 99% 以上的 RTT 都在这个范围内，避免误判。
    

> [!NOTE] 考研计算技巧
> 
> 题目通常会给出第一个样本。
> 
> - **第一个样本的处理**：
>     
>     - $RTT_S = RTT样本$
>         
>     - $RTT_D = RTT样本 / 2$
>         
>     - $RTO = RTT_S + 4 \times RTT_D$
>

## 4. 重传二义性与 Karn 算法

### 4.1 问题：重传二义性 (Ambiguity)

假设发送方发了报文 A，超时了，重传了 A'。过了一会儿收到一个 ACK。

问题：这个 ACK 是确认原来的 A（只是迟到了）？还是确认重传的 A'？

- 如果认为是 A 的：算出的 RTT 会偏长。
    
- 如果认为是 A' 的：算出的 RTT 会偏短。
    
- **后果**：这就搞乱了 Jacobson 算法的采样输入。
    

### 4.2 解决方案：Karn 算法

**规则**：

1. **不采样**：只要报文段被重传了，就不使用该报文段的 RTT 样本来更新 $RTT_S$ 和 $RTT_D$。
    
2. **退避 (Backoff)**：报文段每重传一次，就把 **RTO 增大一倍** ($RTO_{new} = 2 \times RTO_{old}$)。
    
3. **恢复**：直到传输一个**不需重传**的报文段，才恢复使用 Jacobson 算法计算新的 RTO。

## 5. 总结：考研知识图谱

|**知识点**|**核心逻辑**|**考查方式**|
|---|---|---|
|**滑动窗口**|依靠 ACK 前移左沿，依靠 rwnd 调整右沿。|选择题：窗口变化图解。|

|**Karn 算法**|重传不采样，RTO 翻倍。|选择题：应对重传时的策略。|
