## 1. 什么是流量控制？

核心定义：

让发送方的发送速率不要太快，要让接收方来得及接收。

**本质**：

- **点对点**的控制：只涉及发送端和接收端，与中间网络状况无关（那是拥塞控制的事）。
    
- **基于反馈**：接收方通过 TCP 首部中的 **窗口字段 (rwnd)** 告诉发送方自己还能接收多少数据。
    

---

## 2. 核心机制：滑动窗口 (Sliding Window)

TCP 采用大小可变的滑动窗口进行流量控制。

### 2.1 窗口的概念

发送方维持一个 **发送窗口**，其大小取决于两个因素：

1. **接收端窗口 (rwnd, receiver window)**：接收方根据自己接收缓存的剩余空间大小，通过 TCP 首部通知发送方。
    
2. **拥塞窗口 (cwnd, congestion window)**：发送方根据网络拥塞程度估算出的窗口值。
    

考研必背公式：

$$\text{发送窗口的上限} = \min(\text{rwnd}, \text{cwnd})$$

> [!NOTE] 流量控制的视角
> 
> 在讲解流量控制时，我们通常假设网络无限畅通（即忽略 cwnd 或假设 cwnd 很大），主要关注 rwnd 对发送行为的限制。

### 2.2 动态调整过程详解

假设 Host A 向 Host B 发送数据：

1. **初始状态**：B 告诉 A，我的接收窗口 `rwnd = 400`（字节）。
    
2. **发送数据**：A 发送了 200 字节的数据（序号 1-200）。
    
    - A 的已发送未确认字节数 = 200。
        
    - A 的可用窗口（还能发多少） = $400 - 200 = 200$。
        
3. **接收确认与窗口调整**：
    
    - B 收到 1-200，发回确认 ACK（ack=201）。
        
    - 同时，B 的应用层读取数据慢，缓存积压，B 决定缩小窗口，通知 A `rwnd = 300`。
        
4. **窗口滑动**：
    
    - A 收到 ACK=201，窗口后沿前移。
        
    - A 更新发送上限为 300。
        
    - 此时 A 从序号 201 开始，还能发送 300 字节。

## 3. 严重问题一：零窗口与死锁 (Zero Window & Deadlock)

这是流量控制中非常经典的考点，涉及异常情况的处理。

### 3.1 死锁场景复现

1. **B 接收缓存已满**：B 向 A 发送一个报文段，`rwnd = 0`。
    
2. **A 暂停发送**：A 收到后，停止发送数据，等待 B 通知。
    
3. **B 缓存腾出**：一段时间后，B 的应用进程读取了数据，缓存有了空间。B 向 A 发送一个报文段，`rwnd = 1000`。
    
4. **报文丢失**：**这个 `rwnd=1000` 的报文段在网络中丢失了！**
    
5. **死锁形成**：
    
    - A 在等 B 发送“有空”的通知。
        
    - B 以为 A 没收到，或者 B 以为 A 还没准备好发，B 也在等 A 发数据。
        
    - **结果**：双方互相等待，连接挂起。
        

### 3.2 解决方案：持续计时器 (Persist Timer)

为了打破死锁，TCP 为每个连接设有一个**持续计时器**。

- **启动时机**：只要 TCP 连接的一方收到对方的 **零窗口通知**，就启动该计时器。
    
- **超时动作**：若计时器到期（通常时间是一个重传时间 RTO），发送方就发送一个 **零窗口探测报文段 (Zero Window Probe)**。
    
- **探测报文段细节**：
    
    - 仅包含 **1 字节** 的数据。
        
    - **考点细节**：TCP 规定，即使是零窗口，接收方也必须接收：**零窗口探测报文**、**确认报文** 和 **携带紧急数据的报文**。
        
- **结果**：
    
    - 接收方收到探测报文，返回确认，并在确认中给出当前的 `rwnd` 值。
        
    - 如果 `rwnd` 仍为 0，发送方重置计时器，继续等待（在此期间不断发送探测报文，时间间隔通常指数级增加，直到达到由硬性限制的时间间隔，例如60秒）。
        
    - 如果 `rwnd > 0`，死锁解除，恢复数据发送。

## 4. 严重问题二：糊涂窗口综合征 (Silly Window Syndrome)

现象：

TCP 接收方的缓存充满了，而交互式的应用进程一次只从接收缓存中读取 1 个字节（比如 telnet），或者发送方应用进程一次只写 1 个字节。

结果：

发送方发送一个巨大的 IP 数据报（比如 40 字节首部 + 1 字节数据），传输效率极低（有效载荷仅 1/41）。这被称为“糊涂窗口综合征”。

### 4.1 情况 A：接收方引起的 (Receiver-side)

- **原因**：接收方缓存满，应用进程一次只读 1 字节，接收方腾出 1 字节空间，马上通知发送方 `rwnd=1`。发送方就发 1 字节过来，又满了。循环往复。
    
- **解决方案 (Clark 算法)**：
    
    - 接收方不急着通过 `rwnd` 通知发送方。
        
    - **策略**：当缓存空间已满时，**暂时向发送方发送 `rwnd=0`**。
        
    - **等待条件**：直到接收缓存有一半空闲空间，或者有足够空间容纳一个最大报文段 (MSS) 时，再通知发送方具体的 `rwnd`。
        

### 4.2 情况 B：发送方引起的 (Sender-side)

- **原因**：发送方应用进程产生数据很慢，一次产生 1 字节，TCP 就发 1 字节。
    
- **解决方案 (Nagle 算法)**：
    
    - **第一步**：发送方将第一个数据字节先发送出去，把后面到达的数据字节缓存起来。
        
    - **第二步**：当发送方收到对第一个数据字节的确认 (ACK) 后，再把发送缓存中的所有数据组装成一个报文段发送出去。
        
    - **补充条件**：如果数据长度达到了 MSS，也立即发送。
        
    - _Nagle 算法的核心_：**停-等协议**的变种，利用等待 ACK 的时间积累数据。
        

> **[!IMPORTANT] 考研总结**
> 
> - 解决接收方糊涂窗口：**让接收方等待**（等缓存空出一半再通告）。
>     
> - 解决发送方糊涂窗口：**让发送方等待**（使用 Nagle 算法，攒够了或收到 ACK 再发）。
>

## 5. 易混淆辨析：流量控制 vs. 拥塞控制

这是 408 考研和面试中必须区分清楚的概念。

|**特性**|**流量控制 (Flow Control)**|**拥塞控制 (Congestion Control)**|
|---|---|---|
|**控制对象**|**端到端** (End-to-End)|**全局性** (Global)|
|**目的**|防止**接收方**缓存溢出|防止**网络核心**（路由器/链路）过载|
|**参与者**|发送方、接收方|发送方、网络中的路由器、接收方|
|**反馈机制**|接收方直接告知 `rwnd`|发送方通过丢包或延迟**推断**网络拥塞|
|**控制变量**|`rwnd` (接收窗口)|`cwnd` (拥塞窗口)|
|**最终发送窗口**|$\min(rwnd, cwnd)$|$\min(rwnd, cwnd)$|

## 6. 流量控制复习大纲 (思维导图式)

1. **基础**
    
    - 定义：抑制发送速率。
        
    - 手段：滑动窗口协议。
        
    - 信令：TCP 首部中的 `Window` 字段。
        
2. **死锁问题**
    
    - 成因：`rwnd=0` 后，更新报文 `rwnd=1000` 丢失。
        
    - 解决：持续计时器 (Persist Timer) + 零窗口探测报文。
        
3. **效率问题 (糊涂窗口)**
    
    - 现象：大头小身子 (40B Header + 1B Data)。
        
    - 接收方策略：Clark 算法 (攒够一半缓存再说)。
        
    - 发送方策略：Nagle 算法 (攒够 MSS 或收到 ACK 再发)。
